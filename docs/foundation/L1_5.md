L1.5 is everything the host implements beyond denotation, and where a construct is admitted. Its admission rule is the floor's admission test read from above: a surface construct adds no denotation -- every application expands into the five constructors -- or it does not enter here. What refuses to expand goes to L1 as an axiom, or nowhere. The floor never rejects, so rejection is interpretation's job: well-formedness here, and the finite-execution refusals -- bounded reads, decidable matching, termination, boundary hygiene -- in the contract above (L2).

## Matching

- Query -- a universe run against text; it matches one entry, by any face. A query denoting the empty universe matches nothing; emptiness stays meaningless, not invalid.

- Capture -- the floor's `<value, face>` read off a hit. The object already carries the pair, so a capture is a binding, never a store; no operand holds a text field.

- Membership -- matching is set membership: does the text spell an entry? No value or ordinal semantics leak in; the matcher knows only spellings.

- Longest-first -- tile the text longest-face-first (maximal munch); where one face is a proper prefix of another, the longer wins. Declaration order never selects a match.

- Zero-width -- the unit's face is the empty spelling, and no match is ever accepted on it. The unit exists to be a factor (the product identity), not a query.

- Back-references -- the factor family stands in patterns too: inside a query, `{$k}` wherever a universe stands, or `$k` as a pipeline argument (`where 0..$2`), reads factor `k` of the same query -- strictly to its left, since only a bound factor can be read. The admission story is late-bound expansion: the matcher binds factors left to right, so by the time the reading factor is tried its read is bound, and substituting the face -- as it hit, the family's one reading -- turns every attempt into a plain floor query. Expansion parameterized by a binding, never new denotation.

  A face in a pattern position stands as the literal spelling it is; in an argument position it substitutes as a written argument, so the numeral binding rules apply unchanged -- canonicalization is what makes `where 0..$2` a value cut whatever padding the read hit wearing. A read never crosses a declaration: a `$k` in a `uni` or `def` body stands in no query and is refused. Where a hit splits more than one way, the collision rule decides as ever (Emit, below), each split priced under its own bindings.

- Scope -- matching is decidable only where the settlement theorem reaches: closure bodies that are all guarded (closure-free queries always). An unguarded or negative body still denotes -- the floor's totality -- but only semi-settles, so matching it is out of scope: refused by the finite-execution contract (L2), never a denotation failure.

## Names

- `uni name = {...}` -- a declaration; the name stands wherever a universe stands (member, factor, subtraction operand), contributing entry-wise by the floor's splice rule. That is also what makes a name the way to union sub-universes without folding them, since splice spreads where a braced member quotients.
- Reference -- `@name` splices the declaration wherever a universe stands. The sigil is what keeps a name from ever reading as a spelling, so `{cat}` stays the literal face and `{@cat}` the splice. One namespace, resolved at expansion: the registers are its two reserved names -- bare `@` the head, `@0` its zero entry -- and numerals are not declarable, which keeps `@0` free.
- Acyclic -- a name may not reach itself through its declaration, directly or through other names. `&` is the language's only self-reference, and it lives on the floor; acyclicity is what keeps every expansion finite.
- Literal faces -- inside `{}` every character is the spelling it is, whitespace included: `{cat dog}` is the one face `cat dog`, and members divide on `,` alone (`{cat,dog}`, no space after the comma). Only the structural characters (`,` `{` `}` `(` `)` `[` `]` `!` `&` `@` `_` `^` `$` `"` and `\`) are carved out of the alphabet; spell one literally with a `\` escape (a lone `.` is already a literal dot -- only `..` is the range). There is no insignificant whitespace to lay a universe out with -- a space or newline between braces is content, not formatting.

## Definitions

- Form -- `def name params = body`, applied two ways: the modifier pipeline `A[f x g y]` (stages left to right, each stage's result the next stage's operand), and prefix `@name(args)` -- the operand-free invocation used inside another body, its arguments in parens so no whitespace has to separate them from the name. A zero-argument name splices bare, `@name`.
- Substitution -- application replaces the body's parameters with the parenthesized arguments and the operand token `_` with the stage operand; the result is an expression over names, registers, and the floor, and expansion continues until only constructors remain. `_` binds only at a pipeline application: a definition invoked prefix (`@name(args)`) inside another body shares the caller's head (below) but receives no operand, so a `_` in its body is a scope error, never an inheritance. Juxtaposition is always a product -- `@a@b` never applies `a` to `b` -- so application is exactly the parens and the pipeline. Definitions are non-recursive (recursion is the closure's) and acyclic like names, so expansion terminates.
- Head -- registers read the pipeline head, not the stage operand, and a definition invoked inside another body shares the caller's head: one radix rides the whole chain. `{0..9}[where 8..12 pad 1..2]` fills with `0` because the head is `{0..9}`, whatever `where` left in the pipe.
- Numeral parameters -- a parameter written as a numeral or numeral pair (`lo..hi`) binds canonicalized in the head radix: leading zero digits strip, so `aa` binds as `a` (value 0 either way). A lone numeral argument binds a pair parameter as the degenerate pair `n..n` -- the surface's echo of union's "a lone spelling is the singleton case", and already the floor's theorem, since `{2..2}` is `{2}` under the range compression -- so `pad 2` binds `w..w'` at `2..2`. Canonicalization and the degenerate pair are rules of binding, priced with the registers below.
- Exponent -- `A^n` is `A` written adjacent `n` times, iterated product running down to the identity: `A^0` is the unit, by the floor's product-identity theorem. The count is a decimal numeral on the page -- or a parameter that bound one, as `pad`'s `^{w'}` below -- never a value read in any universe: expansion counts, it never denotes, and a count that does not spell a decimal numeral is refused. Counting is the expander's arithmetic and refusal is this layer's privilege, which seats the notation here rather than on the floor's compression list; every application expands into iterated product, so the admission rule holds as written.

## Registers

- The in-language spellings of the expander's metafunctions -- the reads a written body needs that no expression can compute. The precedent is the floor's own bounded range: `{a..z}` = `{a..,!{s..}}` computes the successor `s` at expansion time, and a register is the same move given a token, so that declarations, and not just spec prose, can lean on it.
- `@` -- the pipeline head itself, as a universe. The most primitive read there is: every register is a read of the head, and `@` is the head unread. It anchors the value line to the radix wherever a definition sits in the pipe. On an empty head it reads as the empty universe -- total, in the floor's manner.
- `@lo..hi` -- the pipeline head's value line, cut to the entries at values `lo` through `hi`. Not derivable from `@`: no expression selects an entry by value, so a value cut is its own read, never a cut of the head's spellings. `@0` is the degenerate `@0..0` -- the zero entry, keeping its own spelling exactly as a lone numeral argument keeps `n..n`; `@lo..`, with `hi` absent, is the open case -- every entry from `lo` on, so `@0..` is the whole value line and the family generates as well as cuts. Entries read at their canonical faces, as `@0` always did: the family cuts the value axis and leaves the face axis to the stages that follow it.
- Digit-walk -- the family's expansion, and the reason it is radix-general. The head's entries in value order are the radix's digits, so a bound decomposes into digit positions: numerals narrower than the bound, then one term per position carrying that position's prefix, a cut of the digits below its digit, and free digits to the right. Iterated product and union -- the five constructors, reached by counting positions, which is the expander's arithmetic and not a denotation. No premise about spellings enters, which is the whole difference from cutting the value line with a spelling range: a spelling range needs value order and shortlex to agree, and over a radix whose digits wear wider faces they do not.
- Bounds -- a written bound binds canonicalized in the head radix, as every numeral parameter does, and a bound written as a capture read substitutes the face it hit and then binds the same way. Both bounds are therefore read *in the head's own radix*: the family cuts the value line the head generates, and names positions on that line in the head's own numerals. A hit read under one radix does not cut another radix's value line -- that would be a cast, which nothing here computes (Worked derivations, below). Respelling stays what a fold declares.
- Totality, in the floor's manner: `hi` below `lo` reads as the empty universe, a bound past the head's order type saturates, and an empty head has no entries to cut -- so `@0` reads as the unit there and a fill built on it no-ops. An absent `hi` has no bound to outrun, so the open case never saturates from above: it is the line's tail up to its order type, never past it.
- The inventory, closed: the shortlex successor (the floor's own, no token), numeral-parameter canonicalization and the degenerate pair (binding rules, no token), `@` and the value family `@lo..hi` for the expander, and `$` and `$0` for the emitter with the factor family `$1..$n` addressing the hit's written factors -- read in a template (Emit, below) or standing in a pattern (Matching, above) -- priced on the same shelf. Four tokens and two addressed families, each family an addressing of a token already on the shelf rather than a new one: `$1..$n` addresses the hit `$` names by factor, `@lo..hi` addresses the head `@` names by value. A new register faces the scrutiny a new axiom does -- each is a hole in "the language writes its own std" -- and the finish line is measured by the inventory staying this size.

## Worked derivations

Transformation runs on three axes -- alphabet, value, face -- and none needs a primitive: each dissolves into the floor.

- Alphabet axis -- keeping and dropping entries are intersection and difference, on the floor's compression list.
- Value axis -- the closure generates the value line; cutting it is the one read no expression computes, so the cut is the register family and `where` its pipeline spelling. Its open case is the whole line: `where 0..` (`{@0..}`) is the value line itself -- the head's entries one per value, the zero digit first, then the closure's stages width by width, product order within a width already being value order -- so generating the line and cutting a stretch of it are one mechanism. The register is needed because an expression cuts spellings and nothing else. The digit-walk cuts by position, so the cut is exact over any radix and keeps the value line's order; a spelling range is exact only where value order and shortlex agree -- a premise about the digits' faces, not a theorem about the language. `where` never reads the pipe: it regenerates the value line from the head and cuts it, a generator anchored to the radix rather than a filter of its operand, so its body carries no `_` and it means the same thing at any stage.
- Face axis, by value -- a fold carries a *declared* respelling: an input spelling rides as a later face and the output as face 0, which is transformation without arithmetic. What it does not carry is a cast -- writing a bound value under a *second* universe, decimal to hex, a unary run's length as a decimal numeral. That is value-indexing across two radixes: the value family cuts one head's value line and names its bounds in that head's numerals, so it never crosses. A cast would need the value read as a value rather than as a spelling, which no expression computes and no register here spells.
- Face axis -- subtraction cuts it directly: the floor's subtraction acts on spellings, stripping the face that claims each one, and an entry drops only with its last face. A width cut is therefore a single subtraction of the unwanted widths.

The std that the finish line asks for is written over this surface; its entries are declared in L3, the centralized inventory (`docs/foundation/L3.md`). `char`, the one `uni` the spec seeds, is the floor's code-point set `C` less the noncharacters (the sentinel space, below), and the derivations below work over the std's `str` (every spelling), its width toolkit (`shorter`/`upto`/`longer`), `where` and its top-exclusive sibling `below`, `pad`, and `padfree`.

`pad` is two face cuts: `fill^{w'}` gives every entry its faces from bare up to `w'` extra fills, and the subtractions strip every face too narrow or too wide, each entry surviving on whatever widths remain -- no arithmetic on `w'` needed, since the overshoot faces fall to `longer w'` regardless.

`zeros` through `padfree` are the uncapped pad: `pad` bounds its widths because `w'` feeds an exponent, and dropping the cap dissolves the exponent into a fold -- `zfold` is one entry of order type $1$, so the product `{@zfold _}` moves nothing on the value axis and hangs every zero-padding on the face axis. Matching a `padfree` result stays in scope, since membership decides it; a canonical read of one does not, since every entry wears infinitely many faces -- the read the bounded `pad` keeps.

| Expression | Denotes | Why |
| --- | --- | --- |
| `{0..9}[where 8..12]` | 8, 9, 10, 11, 12 | the value line cut to `8..12`: width-1 digits from 8, width-2 canonicals to 12 |
| `{a..z}[where aa..cc]` | a, ..., z, ba, ..., cc (55 entries) | `aa` binds canonical as `a`, so the width-1 numerals enter the range |
| `{8,9,10,11,12}[pad 2]` | 88, 89, 10, 11, 12 | `@0` is `8`; `shorter 2` strips the bare `8`, `9`; `longer 2` strips `810`, `888`, ... |
| `{0..9}[where 8..12 pad 1..2]` | {8,08}, {9,09}, 10, 11, 12 | head fills `0`; widths 1-2 both legal, so `8` keeps both faces; `010` is stripped |
| `{a,bb}[where a..bbbb]` | a, bb, bba, bbbb | a non-character radix: the digit-walk cuts positions, so values 0-3 come out in order |
| `{a,bb}[where bb..bba]` | bb, bba | values 1-2; a spelling range would cut shortlex here and miss `bba` for `bbb` |

## Emit

Emit is the write half of using a universe against text, and it enters on the bar matching cleared: interpretation, not expression -- no template builds a universe the constructors do not reach, and every read it needs is priced as a register. Two objects and one join rule carry the whole section.

- Text objects and branches -- a **text object** is where spellings live: the document a statement runs against, or a string a template constructs. A **branch** is a span of one text object carrying the capture its match bound. The span (`[start, end]` to the host) and the floor's `<value, face>` are one datum seen twice, since the object's text over the span is exactly the bound face. Only branches cross `=>`: never a detached value, always a pointer into some text.

- Steps -- a statement is a chain of steps joined by `=>`, each a **query** (a universe expression, pipelines included) or a **template** (quoted `"..."`: literal text plus `{{...}}` interpolation sites, each holding one capture read). Arrows are top-level only: inside a brace or a quote, `=>` is literal text.

- Lines -- one declaration or statement per logical line. A brace or quote spanning physical lines stays one statement, a line whose first token is `=>` continues the statement above, blank lines separate nothing, and `//` comments run to end of line at brace depth 0 only, so `{http://x}` stays a face.

- A query step refines: it tiles the branch's text by the matcher above (whose scope rules it inherits), one sub-branch per match, and a query that matches nothing stops the branch -- the guard reading. Tiled matches are disjoint, so commits never contend and the splice needs no conflict clause.

- A template step constructs: it always builds a string, literal text landing as written and each interpolation rendering its read. An incoming branch anchors it -- the string commits over the branch's span, never rolled back, and each interpolation site continues as a sub-branch at its rendered span, carrying its read's binding, so decoration lands but never flows. A template with no interpolation site commits and ends its branch: nothing is left pointing anywhere. No incoming branch at all (a leading template) leaves the string detached: the rest of the chain computes over it and the document never changes.

- Bootstrap, without exception -- a leading query branches into the statement's target; a leading template is the detached string above. The whole-document rewrite is an idiom, not a case: `{@str} => "..."` tiles the entire text as one entry of `str`, maximal munch taking the longest face -- and on an empty document it does not fire, since the one face on offer is the empty spelling and zero-width never matches.

- Capture reads -- the emitter's registers, the match read as `@` is the head read. `$` is the hit as it hit, the bound entry at its bound face; `$0` is its canonical face -- the zero of the face axis, as `@0` is the zero of the value axis. The fold carries the transformation: an input spelling rides as a later face, the output as face 0, and no machinery beyond the floor's pair is needed.

- Factor reads -- `$1..$n`, one read per top-level factor, 1-based since `$0` is taken, being the canonical read. Adjacency is the product, so the hit binds one entry, and an entry of a product is a tuple: `$k` is component `k` of the bound tuple, spelled as it hit over its sub-span -- a pure read of a binding the match already carries.

  Where the hit's spelling splits more than one way, no new rule decides: the floor's collision rule already has, the spelling belonging to its least `<value, face>` claimant. So `{a,ab}{c,bc}` against `abc` reads `$1` as `a` and `$2` as `bc`, the `(ab, c)` split having lost the spelling at the floor. Factors are the written units: an exponent's repetitions stay inside theirs, so `{a}^3{b}` offers `$1` and `$2`, the first reading all three repetitions. The reads are as-it-hit only -- a factor's entries may wear infinitely many faces, matchable but not canonically readable, so there is no per-factor canonical read. The price is `$0`'s: a split the text pins uniquely reads for free, and an ambiguous one streams entries in value order, refusing past the host's budget rather than guessing.

- Contraction -- `query <=> template` is the one iterated statement: the pass is the ordinary statement (tile, commit, splice), re-run until a pass leaves the document unchanged -- a fixpoint. Iteration order is value order, as ever. The statement carries no declared measure: it settles when the rewrite stops moving the document, and nothing on the arrow proves in advance that it will. Bounding a run that never reaches a fixpoint -- refused past the host's work budget rather than left to hang -- is the finite-execution contract's (L2).

- Splice -- a statement's result is its committed strings laid over their spans with the text between kept, at every depth; the flat list with the spans dropped is the extraction view of the same result.

| Statement | Against | Yields | Why |
| --- | --- | --- | --- |
| `{{cat,feline}} => "{{$0}}"` | `my feline` | `my cat` | `feline` binds face 1; `$0` writes face 0 |
| `{a,e,i,o,u} => ""` | `pattern` | `pttrn` | the empty string commits over each match |
| `{@str} => "<b>{{$}}</b>"` | `abc` | `<b>abc</b>` | one branch spans the whole text; decoration lands, `$` re-emits the hit |
| `{a} => {b}` | `banana` | `banana` | a mid-chain query is a guard: no `b` inside an `a`-match, every branch stops |
| `"seed" => {e} => "E"` | anything | unchanged | a leading template is detached: the chain computes `sEEd` off the document |
| `{a,ab}{c,bc} => "{{$2}}"` | `abc` | `bc` | the hit binds `(a, bc)`, not `(ab, c)`: collision gave `abc` to value 1 |
| `{a,b}{$1} => "{{$1}}!"` | `aa ab` | `a! ab` | the second factor re-spells the first: `aa` hits, `ab` never does |
| `{ba} <=> "ab"` | `bbaa` | `aabb` | three passes rewrite; the fourth leaves the document unchanged and stops |

## Sentinels

- `sentinel name` -- a declaration; the name stands wherever a universe stands, denoting one entry wearing one face: a noncharacter the host allocates (U+FDD0 up, in declaration order), the second seed after `char`. Admission is immediate -- the declaration resolves to a `uni` over a lone face, already a leaf of the five constructors -- so the floor never learns sentinels exist.
- Outside the alphabet -- `char` subtracts the noncharacters, so no `@char`-derived universe can touch a sentinel: the only thing that matches a sentinel is its name. Collision with document content is not avoided but unrepresentable, which is what makes the masking idiom sound.
- Engine-private -- sentinels never cross the document boundary. A sentinel is a real noncharacter while the script runs, so statements can match it; at exit every declared sentinel is stripped from the document, so nothing engine-private ships and no cleanup statement has to be written. The way *in* is still guarded: a document that arrives spelling a noncharacter is refused (Unicode reserves them against interchange), the ingest side of the finite-execution contract (L2). Since `char` excludes the noncharacters and ingest refuses any that slip in, the exit strip removes exactly the masks the script wrote and nothing else.
- `{{@name}}` -- the template read that splices a sentinel's face: the only way a sentinel enters text, since nothing else spells a noncharacter. It reads the environment where `$` and `$0` read the hit, which keeps it off the register inventory -- the four tokens stand.

## Diagnostics

- Errors of well-formedness live here: unknown or cyclic name, malformed definition or arity, a register outside a definition body, an operand token no application binds, an exponent count that is not a decimal numeral, a value bound the head radix does not spell, a capture read outside a template or in one no branch anchors, a factor read past the factors the query wrote, a pattern read at or right of the factor it reads or crossing a declaration, a sentinel read of a name that declares none. The operational refusals -- a read past the host's budget, a matcher on an unguarded body, a contracting statement that never reaches a fixpoint within the host's budget, a noncharacter arriving at the document boundary -- are the finite-execution contract's (L2). The floor never rejects, so every rejection is an interpretation refusing a scope, never an expression failing to denote.
- Emptiness is not an error: a query denoting the empty universe matches nothing and says so. Meaningless stays legal; whether to warn is a later layer's taste, not this layer's law.

## North star

The layer's witness is a bubble sort: sentinels mask each line, factor reads and back-references spell the adjacent out-of-order pair, and the contracting statement iterates the swap to a fixpoint -- the sentinels clearing at exit, so no cleanup statement is written. It takes decimals of any magnitude at any padding and re-emits each at the width it arrived -- `where`'s canonical binding makes its cut a value cut whatever padding the read hit wearing, and `padfree` hangs every padding on one entry, so no width cap has to stand in for value order:

```text
sentinel start
sentinel end

uni c      = {@char,!{\n}}
uni line   = {@c,&@c}
uni d      = {0..9}
uni digits = {@d,&@d}

{@line} => "{{@start}}{{$}}{{@end}}"
{@start,\,}{@digits}{\,}{0..9}[below 0..$2 padfree]{@end,\,} <=> "{{$1}}{{$4}},{{$2}}{{$5}}"
```

The statement carries no measure: it iterates until a pass finds no adjacent inversion left to swap, and the line it settles at is the sorted one. What has to hold is that each swap *moves* the document -- strictly reorders a pair, never merely re-dresses it -- or the iteration would spin. The fourth factor's top-exclusive cut secures that: the inclusive `where 0..$2` would also match a value-*equal* pair, whose swap only re-dresses or repeats the document, so `below` -- the value cut less its top endpoint (`{@lo..hi,!{@hi}}` in L3) -- makes an adjacent pair match exactly when it is out of order, the subtracted value-equal band named once in the std rather than spelled at each use. Its entries wear infinitely many faces -- matchable, not canonically readable -- so the sort's template reads every hit as it hit.

The program, witnessed -- one document in, its lines each sorted, the program itself fixed:

| Against | Yields | Why |
| --- | --- | --- |
| `3,1,2` | `1,2,3` | each pass swaps an adjacent inversion; iteration settles at the ascending line |
| `10,9` | `9,10` | value order, not shortlex: `9` precedes `10` though `"10"` precedes `"9"` as text |
| `09,3` | `3,09` | `where`'s value cut ignores the pad; each numeral re-emits at its arrival width |
| `007,7` | `007,7` | equal value: factor 4 strips the value-equal band, so the pair never matches to swap |
| `2,1\n4,3` | `1,2\n3,4` | the start/end sentinels mask each line, so the sort descends each line on its own |
